## 1. Project Goal

Wrap the free video-generation capability of **dola.com** (ByteDance's overseas brand of the Seedance video model, i.e. the overseas version of Jimeng/Doubao) into an **OpenAI-compatible asynchronous API service** via an **account pool**, and distribute it for clients to call.

Full pipeline: `client request (OpenAI format) → account pool picks an account → browser UI submission (pass the slider) → poll for video completion → download and re-host → return video URL`.

Key background:
- dola.com has **no official public API**; video generation goes through the web frontend interface and must be reverse-engineered.
- Free quota: **2 videos per account per day** (UI copy: 1 video = 2 credits), so an account pool is required to scale up capacity.
- Login method: **Google OAuth**.
- Region restriction: requires a **JP/KR egress IP** (direct connection from mainland China does not work).

## 3. Evolution of the Core Technical Approach (Why We Did It This Way)

1. **HTTP reverse engineering (raw aiohttp requests)** — protocol fields were successfully reverse-engineered (`dola_client.py`), but submitting a video always triggered the shark risk-control slider (`710022004 slide`).
2. **Raw fetch from inside the page** — still hit the slider. Root cause: the frontend's real requests carry an **`a_bogus` signature** (generated by webmssdk), which raw fetch lacks, so risk control spots it at a glance.
3. **Real UI flow (current mainline, video output verified)** — click "Create video" → type → press Enter, and the frontend signs and submits by itself. Risk control may still pop the slider (headless + datacenter IP), but **the slider can be solved** (OpenCV gap + human-like trajectory), after which the frontend automatically retries the submission.
4. The video-polling protocol has been updated to the current version as of 2026-08 (see §4.1); the old flat body returns `712010202`.

**Acceptance status (2026-08-22)**: ✅ Two videos fully generated and downloaded (orange cat 10s / snowy mountain lake 10s), ✅ FastAPI async two-stage API verified end-to-end.

## 4. Completed Features

### 4.1 Protocol Knowledge (current version, 2026-08)

**Submission (must go through the UI; the frontend signs a_bogus)**:
- Entry point: the "Create video" chip below the input box on the home page (in the ja-JP locale the copy is `動画を作成`, "Create video").
- Frontend body: `chat_ability={ability_type:17, ability_param:{model:"seedance_v2.0",duration}}`, with a localized text prefix (ja: `生成された動画：{prompt}` "Generated video: {prompt}"; zh variants: `生成影片：{prompt}，{ratio}` "Generate video: {prompt}, {ratio}").
- query contains `a_bogus`, `device_id`, `web_id`, `tea_uuid`, `pc_version=3.32.61`, etc., generated by webmssdk; **cannot be called raw**.

**Video polling (can be fetched from inside the page, no signature needed)**: `POST /im/chain/single`
- body must wrap `uplink_body.pull_singe_chain_uplink_body`:
  `{conversation_id, anchor_index: Number.MAX_SAFE_INTEGER, conversation_type: 3, direction: 1, limit: 20, ext:{}, filter:{index_list:[]}}`
  plus `sequence_id: uuid, channel: 2, version: "1"`.
  (The flat body in `dola_client.py` is the old protocol, returns 712010202, do not use.)
- query needs no msToken/a_bogus: `version_code=20800&language=ja&device_platform=web&doubao_device_platform=web&aid=495671&real_aid=495671&pkg_type=release_version&pc_version=3.32.61&doubao_pc_version=3.32.61&region=JP&sys_region=JP&samantha_web=1&web_platform=browser&use-olympus-account=1&web_tab_id=<uuid>`.
- Video-completion detection: inside `downlink_body.pull_singe_chain_downlink_body.messages[].content` (a JSON string that must be parsed), `block_type=2074` and `creations[].type==2` → `video.download_url` (a temporary CDN link, with `download=true`).
- `conversation_id` retrieval: after UI submission the URL changes from `/chat/local_<ts>` to `/chat/<numeric id>`.

**Constants**: `DOLA_AID="495671"`, `DOLA_BOT_ID="7339470689562525703"`, `VERSION_CODE="20800"`.

### 4.2 Slider Solving (verified, pass rate about 1-2 attempts)

ByteDance verifycenter (overseas rmc-captcha):
- After triggering, the frontend loads an iframe whose URL contains `bdcaptcha.html`; the backend is `verify-s.byteintlapi.com/captcha/get?subtype=slide`.
- Inside the iframe: background image `~tplv-w5pjy1c2y6-2.jpeg` (552×344), slider piece `~tplv-w5pjy1c2y6-1.png` (110×110 transparent).
- Drag button class: **`.captcha-slider-btn`** (note that `[class*="slider"]` also matches the track `captcha-slider-box` by mistake).
- Gap detection: `gap.py` OpenCV (alpha contour Canny → background-edge matchTemplate); measured conf 0.23-0.39 but the position is correct; **wait for the image to finish loading (naturalWidth>0) before computing the scale**, display width 340 / natural width 552.
- Human-like trajectory: smootherstep main stroke + 3-9px overshoot and settle + y-axis jitter, total duration ~1s, passes.
- After passing, the iframe disappears and the frontend **automatically retries the submission**; on failure the same image stays put (meaning the drag had no effect — check the selector).
- The slider is **not triggered every time** (after a given profile passes once, subsequent requests may be let through directly).

### 4.3 OpenAI-compatible API (verified end-to-end)

- `POST /v1/videos/generations` → `{id, status:"queued"}`; `GET /v1/videos/{id}` → `{status, video_url}`.
- After generation the video is downloaded into `downloads/` and served as a permanent link via the `GET /videos/<file>` static service (replacing the temporary CDN link).
- `GET /health` → account quota status.
- Account pool `browser_pool.py`: scans `accounts/*/`, 2 videos per account per day (SQLite counting, conservative: only counted on success/quota error), same-account mutual exclusion via asyncio.Lock, automatic account switching when quota is insufficient.

### 4.4 Login-state Capture (carried over)

- `login.py <account name>`: headful manual Google login; on detecting sessionid, saves the profile to `accounts/<name>/`.
- `verify_login.py`: headless verification of login state.
- Existing profile: `accounts/acc1/`.

### 4.5 Automatic Account Addition (fully automatic Google OAuth, verified)

`add_account.py <account name> "email----password----totp_secret"`:
dola login popup `Googleで続ける` ("Continue with Google") → Google v3 login state machine → OAuth redirect back → dola age confirmation → sessionid written into the profile.
The state machine handles each page: choose account / email / password / consent / age confirmation, until it leaves accounts.google.com.

Pitfalls (all resolved; keep them in mind when changing the code):
- The Google v3 email field is `#identifierId` and is **type=text** (not type=email); the password field is `input[name="Passwd"]`.
- The consent page also displays the email text, so **the account-chooser page must be identified by the URL containing `accountchooser`**, otherwise it misclicks the account strip on the consent page.
- The consent page's "Continue" button must be clicked via `button:has-text('继续')` / `[role='button']:has-text('继续')` (also matches ja `続行` / en Continue).
- The dola age-confirmation popup (`18歳以上`, "18 years or older"): the normal selector for its OK button does not work; use a **JS dispatch click** on the leaf node.
- Google cookies linger in the profile: a second login goes choose account → consent (no password).
- TOTP is implemented with the standard library (`totp()`), no third-party dependency.

After login, verify with `verify_login.py <account name>`; the account pool (`browser_pool.py`) auto-discovers new accounts by directory, no service restart needed.

## 7. Known Technical Debt

1. **locale coupling**: the UI entry copy is hardcoded to ja-JP `動画を作成` ("Create video"); changing the locale requires changing `VIDEO_BTN`. Using an icon/attribute selector would be more robust.
2. **headless fingerprint**: sec-ch-ua exposes `HeadlessChrome`, which is very likely why risk control pops the slider (solvable, but adds latency). For production consider headful + xvfb or further fingerprint patching.
3. **duration/ratio selectors are best-effort**: the UI dropdown option copy is not fully understood, and a failed setting falls back to the default 10s.
4. **re-hosting is still local static**: `/videos/` is only reachable from the machine hosting the service; external distribution needs OSS or a public-IP machine.
5. **Quota counting may drift from dola's actual credits** (1 video = 2 credits; the UI has "remaining credits" copy). Not counting quota on failed retries is intentional and conservative.
6. **dola_client.py's polling body is outdated** (flat structure); if the HTTP version is ever revived it must be updated per §4.1.
7. **The slider fallback is implemented but not 100%**: when a trajectory is rejected it relies on retries (up to 3); consecutive failures require switching IP/cooldown.

## 9. Constraints and Potential Risks

1. **Region wall (hard constraint)**: dola requires a JP/KR egress; the proxy is passed explicitly to the browser (`config.PROXY`, default `http://127.0.0.1:7890`), not relying on the system proxy.
2. **Slider risk control (core risk)**: the UI flow + a solvable slider is currently the best solution; ByteDance may upgrade the captcha at any time (change trajectory detection / switch form), and the `bdcaptcha.js` archive can be used to keep up with class names.
3. **Capacity bottleneck**: 2 videos/account/day, so pool size = capacity ceiling.
4. **Login-state lifetime**: ~60 days, requires renewal.
5. **Frontend-change risk**: entry copy/dropdowns/polling protocol may all change; `diag_raw2.py` can quickly capture the current request format.

## 11. Admin Panel (v0.3.0)

- Visit `http://127.0.0.1:8000/`, four main tabs: Dashboard / Account management / Task list / API keys.
- Admin auth: `config.ADMIN_KEY` (env `DOLA_ADMIN_KEY`); empty = panel login-free (dev mode). The client sends the `X-Admin-Key` header on every request; the frontend stores it in localStorage.
- The scheduling switch and risk-control cooldown feed directly into pool selection: `generate_video` skips accounts with `scheduling=0` or `cooldown_until>now`; catching `RiskControlError` automatically sets a 30-minute cooldown (`COOLDOWN_SEC`).
- Account metadata table `accounts_meta` (pool_usage.db): scheduling/note/created_at/last_used_at/login_ok/login_checked_at/cooldown_until; the pool auto-creates rows with `INSERT OR IGNORE` when scanning the directory.

### 11.1 admin endpoint family (all go through `X-Admin-Key`)
- `POST /api/admin/login` | `GET /api/admin/accounts` | `PATCH/DELETE /api/admin/accounts/{name}` | `POST /api/admin/accounts/{name}/verify` (headless login-state verification, ~7s) | `POST /api/admin/accounts` (background add-account task, 202) | `GET /api/admin/jobs` (add-account task status) | `GET /api/admin/tasks?limit=` | `GET /api/admin/stats` | `GET/POST/PATCH/DELETE /api/admin/keys`.

### 11.2 API key semantics (used by client calls to /v1)
- No auth only when "`config.API_KEYS` is empty AND the DB has no enabled key"; otherwise `Authorization: Bearer <key>` is required.
- env keys (`DOLA_API_KEYS`) are always valid and read-only in the panel; panel-created keys are stored in the `api_keys` table of `tasks.db` (`sk-` + 32 hex, enable switch, last_used_at throttled to update every 60s).
- Disabling/deleting takes effect for callers immediately; deleting all keys returns to no-auth.

## 13. Automatic Account Switching on Daily Limit (2026-08-22)

- `video_worker_ui.py` recognizes Dola's Japanese copy `動画生成の1日あたりの上限に達しました。明日またお試しください。` ("You have reached the daily limit for video generation. Please try again tomorrow.") and raises `AccountLimitedError`.
- After catching it, `browser_pool.py` immediately caps that account's local usage at `DAILY_LIMIT=2`, skips the current account and moves to the next, without waiting for the 300s timeout.
- When all accounts that have scheduling enabled and are not in cooldown are capped, the create endpoint returns HTTP 429 directly; if an already-queued task only discovers the cap during execution, the task status is failed and the error starts with `429:`.
- Measured on 2026-08-22: after `acc1` returned the daily limit it was auto-marked `2/2`; `acc2` was already `2/2`; task `video_7c468876bf224f76971fef69067ed49e` finally recorded 429; subsequent new requests returned HTTP 429 directly.

## 14. Rate-limited Account Recovery Scheduling (2026-08-22)

- `accounts_meta` gains `rate_limited_until` / `limit_reason`.
- After Dola returns the daily limit, the account is immediately marked "rate-limited", and `_schedulable()` always skips it before the recovery time; it does not rely only on `usage.used=2`.
- The default recovery point is 00:00 the next day, Japan time (`DOLA_LIMIT_RESET_TZ` is configurable; when the runtime lacks tzdata it uses a UTC+9 fallback for Asia/Tokyo). This time acc1/acc2 were marked with a recovery time: 2026-08-23 00:00 (Japan time).
- After expiry, `list_accounts()` automatically clears the rate-limit flag; the day's usage query naturally resets to zero on the new date, and the account re-enters scheduling.
- The panel shows the account status as "rate-limited until YYYY-MM-DD HH:MM"; when all accounts are rate-limited, new requests return HTTP 429 directly.

## 15. Long-video Timeout Strategy (2026-08-22)

- Dola's 2.5/30s page shows an estimate of about 15 minutes; the worker automatically uses at least a 1200s polling timeout for `duration=30`.
- A normal polling timeout no longer automatically switches accounts and resubmits: once a conversation_id has been obtained, Dola may still be generating, and switching accounts would cause duplicate quota consumption/duplicate videos.
- Only when Dola explicitly returns the daily limit (AccountLimitedError) or a risk control (RiskControlError) does it automatically switch accounts.
- The first 2.5/30s test on 2026-08-22 was resubmitted from acc3 to acc4 because of the old 300s strategy; the final file was 30.04s. This was later fixed and the service restarted.

## 16. Credit Pre-check and conversation Recovery (2026-08-22)

- `accounts_meta` gains `credit_balance` / `credit_checked_at`; the "remaining N points/ポイント/积分" ("remaining N points") copy in the polling response is cached to the account.
- When a balance is known to be below `DOLA_VIDEO_REQUIRED_POINTS` (default 2), the account is skipped before generation and marked credit-insufficient; when all accounts are known to be insufficient, HTTP 429 is returned. When a new account's balance is unknown it is not wrongly blocked, and the first submission is still allowed to wait for Dola to return the balance.
- `tasks` gains `conversation_id`, `deadline_at`, `last_poll_at`, `failure_code`. Once the Dola conversation_id is obtained it is persisted immediately; polling updates last_poll_at every 30 seconds.
- On FastAPI startup, `queued/processing + conversation_id/account` tasks are recovered by polling the original conversation, without re-sending the prompt; tasks past their deadline only finish, they are not resubmitted.
- The polling ceiling for 30-second tasks is fixed at at least 1800 seconds (30 minutes); a normal timeout does not auto-switch accounts, to avoid duplicate charges.
- Dola currently has no stable standalone balance endpoint, so the pre-check prefers the cached balance; when the balance is unknown it uses a no-wrongful-blocking policy.

## 19. Watermark-free Video Download (2026-08-22)

- Dola's `video.download_url` is a watermarked address (usually `lr=cici_ai`) and can no longer be used directly as the final download source.
- The `video.video_model` JSON in the generation response contains `video_list.*.main_url` (base64-encoded). Decoded, it is a watermark-free video link with `lr=unwatermarked`.
- `video_worker.POLL_JS` now returns `videoModels`; `extract_unwatermarked_url()` picks the main_url with the highest bitrate, and only falls back to the ordinary `download_url` if parsing fails.
- `video_worker_ui.poll_conversation()` is wired up to prefer watermark-free downloads, so all new tasks return the watermark-free version.
- Measured on the image-reference task `video_e74f2b89f87745c2adc730b8dfd5fd8e`: comparing the watermarked original file with the watermark-free main_url confirmed it, and it currently returns the watermark-free file: `https://<quick-tunnel>.trycloudflare.com/videos/acc5_20260822_234820.mp4`.
